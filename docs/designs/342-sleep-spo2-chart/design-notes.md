# 야간 SpO2 그래프 — 디자인 노트 (#342)

## 브리프

수면 상세 페이지에 야간 SpO2 시계열을 넣는다. 데이터는 1분 epoch × 260~463 포인트.
**이 차트의 단일 목적**: 사용자가 이미 보고 있는 세 숫자(평균/최저/최고)가 답하지 못하는 질문 —
"최저값이 **언제**, **얼마나 오래** 있었나" — 에 답한다. 단발 dip 과 지속 구간의 구별.

## 제약 (선택이 아닌 전제)

이 화면은 신규 페이지가 아니라 **기존 수면 상세 페이지에 끼워 넣는 카드**다. 독자적 아이덴티티를
주장하면 같은 페이지의 "수면 점수 세부" · "바이탈 지표" 카드와 충돌한다. 따라서 컨테이너 · 타이포 ·
축 스타일은 `src/components/sleep/SleepScoreChart.tsx` 의 기존 컨벤션을 **그대로 상속**한다.

디자인 자유도는 (1) 색 (2) Y축 스케일 (3) 최저 지점 표현 — 이 세 축에만 쓴다.

## 결정 3건

### 1. Y축 하한은 데이터를 따른다 — 고정하지 않는다 (Codex P2 반영)

`SleepScoreChart` 는 `[0, 100]` 을 쓰지만 그대로 따르면 실제 변동(83~100)이 하단 20% 에 눌려
**차트가 거의 평평한 직선으로 보인다**. SpO2 는 좁은 대역에서 의미가 발생하는 지표다.
기본 하한 `80`, 그보다 낮은 관측이 있으면 `[min-2, 100]` 으로 확장.

**하한을 임의로 막지 않는다.** 초안은 이상치 대비로 `Math.max(70, …)` 을 넣었으나, Recharts 는
기본 `allowDataOverflow={false}` 라 지정 domain 보다 데이터가 낮으면 **domain 을 데이터에 맞춰
되늘린다** — 하한 지정이 사실상 무효였고 코드만 의도를 잘못 주장하고 있었다.

`allowDataOverflow={true}` 로 잘라내는 선택지는 버렸다. 실측 저점을 그래프에서 지우면 Stat 카드의
최저값과 어긋나는데, 이는 `readingConfidence` 필터링을 넣지 않은 이유(결정 3)와 정확히 같은 문제다.
**낮은 값이 있으면 스케일이 눌리더라도 보여주는 쪽**이 맞다.

대신 눈금을 하한에 맞춰 생성해(`spo2ChartYAxis`), 확장된 구간이 라벨 없이 남지 않게 한다.
평상시 `[80,85,90,95,100]`, 저점이 낮으면 균등 간격으로 재생성.

### 2. 최저 지점을 **경고색으로 칠하지 않는다** — 이번 디자인의 실질적 리스크

일반적 선택은 최저 지점과 90% 이하 구간을 빨강/앰버로 칠하는 것이다. **하지 않는다.**

v2.26.2(#338) 에서 확정한 정책: 이 사용자의 최저 SpO2 baseline 은 83~88 이라 절대 임계 경고를
걸면 측정된 모든 밤이 "위험" 으로 표시된다. 리포트 문구에서 걷어낸 오탐을 차트가 색으로 되살리면
같은 실수다.

대신 최저 지점을 **fuchsia-300** 으로 찍는다 — 눈에 띄되 위험 신호가 아닌 색. 의미는
"위험" 이 아니라 **"이 밤에서 가장 주목할 지점"**. 90% 참조선도 라벨을 "기준" 이 아닌 **"참고"** 로 쓴다.

이 선택의 대가: 실제로 위험한 야간이 와도 차트가 스스로 경고하지 않는다. 수용한다 —
경고는 baseline 대비 추세를 볼 수 있는 AI 어드바이저의 역할이고, 차트의 역할은 정확한 관측 제시다.

### 3. `readingConfidence` 기반 필터링 없음

1~27 범위로 관측되나 의미가 문서화되어 있지 않다. 임의 임계로 저신뢰 포인트를 숨기면
**최저값이 그래프에서 사라져 Stat 카드(84)와 차트가 어긋나는** 더 나쁜 문제가 된다.
전 포인트를 그린다.

### 4. X축은 카테고리가 아니라 수치 시간축 (Codex P2 반영)

초안은 `HH:mm` 문자열을 카테고리 축으로 썼다. 이러면 **살아남은 포인트가 등간격으로 배치**되어
60분 센서 dropout 을 사이에 둔 두 포인트가 1분 간격 포인트와 같은 거리로 그려진다. 이 차트의
단일 목적("최저가 언제, **얼마나 오래**")을 정면으로 훼손한다.

`type="number" scale="time"` + `tickFormatter` 로 교체. 실측 왜곡은 ≤6% 로 작았지만, 목적이
지속 시간 판독인 이상 축이 시간을 왜곡하는 설계는 유지할 수 없다.

**공백 끊기 임계는 10분**. 수치 축만으로 간격은 이미 정확히 표현되므로(5분 공백 = 1분 간격의 5배 폭),
추가로 선을 끊는 것은 "보간조차 신뢰할 수 없다" 는 별개의 주장이다. 실측 6야간에서 5~6분 공백은
야간당 2~3회 있는 정상 재측정 주기라 이걸 끊으면 차트가 이유 없이 조각난다. 10분 이상만 끊는다.

### 5. 시간 포맷터는 `number | Date` 를 모두 받아야 한다 (Codex P1 반영)

`scale="time"` 축은 내부적으로 d3 `scaleTime` 을 쓰고, `.ticks()` 는 **도메인이 숫자여도 Date 객체를
반환**한다. 포맷터가 숫자를 가정하고 `value + 9h` 를 하면 `Date + number` 가 **문자열 결합**이 되고,
그 문자열을 다시 파싱하면 원래 instant 로 돌아와 오프셋이 통째로 사라진다.

증상: **축은 UTC(`15:00`), 헤더는 KST(`00:00`) 로 9시간 어긋남.** 차트가 "언제" 를 틀리게 말하는
가장 나쁜 실패다. `getTime()` 정규화를 포함한 `formatEpochKST` 를 `src/lib/format.ts` 로 올려
축·툴팁·헤더가 같은 함수를 쓴다.

실측 확인 (d3 `scaleTime` tick 을 그대로 통과):
```
축 tick (KST): 00:00  01:00  02:00 … 07:00
시작/끝: 23:34 / 07:31   헤더 최저: 00:54
```

## 시그니처

**주석 달린 최저 지점** — 값 + KST 시각을 헤더와 플롯 양쪽에 mono 로 표기.
세 개의 Stat 숫자가 알려줄 수 없는 유일한 정보이고, 이 차트가 존재하는 이유 그 자체다.

## 덜어낸 것

- 수면 단계(`sleepLevels`) 배경 밴드 오버레이 — 정보는 늘지만 이 카드의 단일 목적을 흐린다. 이슈에서도 제외 항목
- 심박 이중 축 — 같은 이유
- hover 크로스헤어 커스텀 — 기본 Tooltip 으로 충분. 장식이 목적을 앞서지 않게

## 접근성 / 반응형

- 색만으로 최저 지점을 전달하지 않는다 — 헤더에 텍스트로 `최저 84% · 03:12` 병기
- `ResponsiveContainer` + 모바일에서 X축 `interval="preserveStartEnd"`
- 데이터 없는 야간(미측정)은 카드 자체를 렌더하지 않는다 — 빈 차트보다 부재가 정직하다
